Existing functionality

The artifact is Travlr Getaways, a travel booking site I built in CS 465. It runs on the MEAN stack: MongoDB with Mongoose for storage, Express for the API, and Angular standalone components for the front end. Admin access goes through JWT. For the capstone I am re-theming it into a game server browser with a mod browser alongside it, because both of those are the same problem shape and reusing the structure costs me nothing.

The walkthrough starts with the running application. The API is up on port 3000 and the Angular admin client on 4200, both out of WSL. Most of the public site is static. The travel listing is the part actually reading from the database, and that listing is what becomes the server browser. On the admin side I sign in with JWT, edit a trip, add a new one, and refresh the public page to show the record come through.

From there I go into the code. Under app_api the three pieces that matter are models, routes, and controllers. travlr.js holds the trip schema and defines which fields are required, with code carrying a unique index and name carrying a plain one. user.js holds the account fields, hashes the password, and issues the JWT on login, which is a lot of responsibility for a single model file. The route table in index.js maps each URL to a controller function and decides which routes are open and which need a valid token. The trips controller handles create, read, update, and delete. On the Angular side, trip-data.service.ts is what actually calls the API. The entry point is app.js, which wires up Express, connects the database, applies middleware, and mounts the routes.

Code analysis

The first problem is structural. Every function in the trips controller does two jobs. It handles the request and response, and it talks to Mongoose in the same body. Trip.find is called directly inside the handler. That means the controller knows the storage engine, so I cannot test the handler without a live database, and I cannot change how the data is stored without rewriting the controller. Those two concerns are stuck together.

Second is a logic issue in tripsFindByCode. It looks up one trip but uses .find, which returns an array, so a single lookup comes back as a list with one element in it and everything downstream has to reach into index zero. findOne returns the document or null and is the right shape. Nothing is broken by this. It is the kind of small wrong shape that spreads, because every caller ends up written around it.

Third is efficiency at the database. Only code and name are indexed. Any query that is not a code lookup does a full collection scan, so Mongo reads every document to find matches. On five seed trips that does not matter. On a server browser holding tens of thousands of records it does. There is also no test coverage anywhere near the queries or the indexes, so nothing tells me whether a query returns what it should.

Fourth is error handling. The try/catch blocks in the controller return a status code and a message, which is not wrong on its own, but there is no logging, so a production failure leaves no history and no stack trace to work from. The raw error object also goes straight back to the client, which hands whoever made the request internal detail they do not need. I hit this live while setting up the demo: the API was down and what came back was the literal error instead of anything a user could act on.

Fifth is security, and this is the area I am least confident in. The user model salts and hashes by hand on top of the crypto library instead of using a vetted password hashing library, and the iteration count is set far too low. Separately, the route table checks whether a request carries a token and stops there. A valid token gets you everything. For a server browser where users submit their own listings I need permissions, not just proof of login, and that check does not belong inline in the router. Unsanitized query input also reaches Mongo, which is an injection surface.

Enhancement plan

Software design and engineering. Put a repository layer between the controller and Mongoose. The controller calls an interface, something like findPage and countMatching, and the repository is the only thing that knows Mongoose exists. That makes the controller testable without a database and lets storage change underneath it. On the client, turn the trip-specific browse view into a reusable component driven by config objects so the server browser and the mod browser share it, and move the hardcoded API URL into config. I said on camera that I was not going to abstract before I had two real uses, so the plan was to build the server browser first and pull the shared piece out once the mod browser needed it.

Algorithms and data structures. Stop handing back whatever the database returns in whatever order it comes out. Score each server on player count, ping, and uptime, sort by that score, and tie-break ascending on name so float scores that land equal still produce a stable order. The factors are pluggable so the mod browser can reuse the engine with different weights. Favorites feed into the score as a boost, not as a hard pin to the top. For search-as-you-type, walk a prefix trie so typing D, then R, then A narrows down the tree instead of rescanning the whole set on every keystroke.

Databases and security. Index the fields I actually query and prove the change with explain(), showing the query move from a collection scan to an index scan. Whitelist query input so only expected fields get through and operator objects get rejected, which closes the injection surface. Add a role and ownership check on writes so a token alone does not authorize everything. Add a favorites collection so the boost has something to read from.

Where the finished work diverged

Two things came out differently once I was in the code.

On camera I said I would swap the hand-rolled hashing for bcrypt. I stayed on PBKDF2 and raised the iteration count to 210,000 instead, and I store the iteration count on each user record so existing accounts stay valid and get rehashed at next login, which is the only moment the plaintext password is available. Swapping the algorithm outright would have invalidated every account already in the database, and the work factor was the actual finding.

I also said findByCode should become findOne. It ended up going through findAll with a code filter. findOne is the correct call in isolation, but changing the return shape would have broken every caller written against the array, and the repository interface was the thing under test. The shape stayed and the coupling problem got solved.

One more thing worth recording. All sixty unit tests passed and an audit script cleared sixty-six checks while the API was still returning 2,938-byte HTML stack traces to unauthenticated requests. The error handling finding above is real, and my own tests did not catch it. A live request in a browser did.
